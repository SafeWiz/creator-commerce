# MCP server for Cece's tools

Date: 2026-09-30

## Problem

Cece answers questions about a user's products, sales, purchases and downloads
from inside the dashboard. Users who work in their own AI clients — Claude,
ChatGPT, Cursor — want the same answers there, next to the rest of their work.
The Cece spec built its tools for exactly this: `CECE_TOOLS` in
`lib/server/tools/` are transport-neutral, and the whole-branch review
confirmed an MCP adapter can register them as they are.

## Scope

- A remote MCP server at `/api/mcp` exposing all nine Cece tools, read-only,
  as the signed-in user.
- OAuth 2.1 authorization for MCP clients through Better Auth's `mcp` plugin,
  with a consent screen on every new authorization.
- Discovery metadata under `/.well-known/`.
- A Cece guide topic telling users how to connect.
- Out of scope: rate limiting (TODO), a connected-apps / revocation UI (TODO),
  personal access tokens, write tools, MCP resources and prompts, CORS for
  browser-based clients.

## Decisions

- **OAuth via Better Auth's `mcp` plugin** (installed `better-auth@1.6.24`).
  Hosted clients (Claude and ChatGPT connectors) speak OAuth, and the plugin
  provides dynamic client registration, PKCE, token issuance, discovery
  metadata and `withMcpAuth` for the route. Rejected: personal access tokens
  (hosted clients can't use them; we would own token storage and revocation),
  and both.
- **Consent on every new authorization.** A client registers itself and names
  itself, so the user's decision is the only check on it. The plugin shows
  `consentPage` only when the request carries `prompt=consent`
  (`better-auth/dist/plugins/mcp/authorize.mjs`), which most MCP clients do not
  send — so the app forces it (see Design). Refresh tokens keep this to once
  per connection rather than once per call.
- **No rate limit in v1.** The client's model does the reasoning, so a call
  costs one bounded DB read, not model tokens. Recorded in TODO with the
  cheap fix (`ai_generations`, `feature = 'mcp'`, `recordGenerationWithinLimit`).
- **No revocation UI in v1.** Tokens expire on Better Auth's defaults. Recorded
  in TODO.
- **`mcp-handler` for transport.** Vercel's adapter serves MCP from a Next
  route handler over stateless Streamable HTTP, which fits serverless: no
  session pinning, no Redis. Rejected: wiring `@modelcontextprotocol/sdk`'s
  transport by hand (more code for what the adapter already does), and a
  standalone MCP service (a second deploy and a second copy of env and DB
  config).

## Design

### Layers

```
lib/server/auth.ts                  + mcp plugin, + three before-hooks and an after-hook
lib/server/db/schemas/auth.ts       regenerated by `npm run schema:better-auth`
drizzle/00xx_*.sql                  generated
lib/server/mcp/server.ts            registerCeceTools(server, ctx, { onError })
lib/server/request/mcp.ts           handleMcp — withMcpAuth + mcp-handler
app/api/mcp/route.ts                GET/POST/DELETE = handleMcp, maxDuration = 30
app/.well-known/oauth-authorization-server/route.ts   oAuthDiscoveryMetadata(auth)
app/.well-known/oauth-protected-resource/route.ts     oAuthProtectedResourceMetadata(auth)
app/(auth)/oauth/consent/page.tsx   consent card (server) + client form
lib/server/ai/cece/guide.ts         + 'connect-your-ai' topic
```

Boundaries, the same as Cece's:

- `lib/server/mcp/` is the MCP counterpart of `lib/server/ai/cece/ai-sdk.ts`.
  It imports `CECE_TOOLS`, the MCP SDK's server type and `appUrl`; never
  `lib/server/request/`, never `@sentry/*` — the error reporter is injected.
- `lib/server/request/mcp.ts` is the only request-scoped entry: `withMcpAuth`
  reads the bearer token from the request.
- Identity is `token.userId` → `ToolContext`. No tool changes; no tool input
  carries a user id.

### Adapter — `lib/server/mcp/server.ts`

`registerCeceTools(server, ctx, { onError })` registers every tool in
`CECE_TOOLS` under its `name`, `description` and zod `inputSchema`, plus
`annotations: { readOnlyHint: true, openWorldHint: false }` — every Cece tool
reads and nothing else, and `readOnlyHint` is what lets a client skip asking
the user before each call. For each call:

- The result is one text content item, `JSON.stringify(output)`. No
  `outputSchema`/`structuredContent` — the tools have none.
- Links are made absolute: a generic walk over the output replaces any string
  that starts with `/` under a key ending in `link` or `Link` with
  `new URL(value, appUrl).href`. A relative path means nothing to a client
  outside the app.
- A throw goes to `onError(error, toolName)` and becomes
  `{ isError: true, content: [{ type: 'text', text: TOOL_FAILURE_MESSAGE }] }`
  — MCP's native tool-error result. `TOOL_FAILURE_MESSAGE` lives in
  `lib/server/tools/shared.ts` and is the same sanitized line Cece's own
  adapter (`lib/server/ai/cece/ai-sdk.ts`) sends; the original error never
  leaves the server.

### Route — `lib/server/request/mcp.ts`

`handleMcp = withMcpAuth(auth, (request, token) => createMcpHandler(server =>
registerCeceTools(server, { userId: token.userId }, { onError }), ...)(request))`,
with `onError` reporting through `console.error` and Sentry. `mcp-handler` 2.2
has no `basePath` option — the route it's mounted at is the mount, nothing to
configure. Mounted at `app/api/mcp/route.ts`, which exports `GET`, `POST` and
`DELETE` as `handleMcp`, with `maxDuration = 30`: tool calls are short DB
reads. `createMcpHandler` serves this statelessly (`legacy: 'stateless'`, the
SDK's default): a fresh server per request, no session to resume, so `GET` and
`DELETE` are answered `405` by the SDK itself — only `POST` does anything.

A missing, expired or unknown token is `withMcpAuth`'s 401, carrying
`WWW-Authenticate` with the protected-resource metadata url, which is how a
client discovers where to authorize. Invalid tool input is rejected by the MCP
SDK against the zod schema before any DAL call.

### OAuth flow

```
Client                               Creator Commerce
 POST /api/mcp (no token)  ────────▶ 401 + WWW-Authenticate: resource_metadata=…
 GET  /.well-known/oauth-*  ───────▶ metadata → authorization server /api/auth/mcp/*
 POST /api/auth/mcp/register ──────▶ dynamic client registration
 browser → /api/auth/mcp/authorize
   ├ signed out → /login?<authorize params>  (oauthAuthorizeQuery keeps the request)
   │   sign in or sign up → window.location.assign back to /api/auth/mcp/authorize
   └ signed in → (forced consent) → /oauth/consent?consent_code&client_id&scope
        Allow → POST /api/auth/oauth2/consent { accept: true }  → client redirect with code
        Deny  → POST /api/auth/oauth2/consent { accept: false } → access_denied
 POST /api/auth/mcp/token ─────────▶ access + refresh token
 POST /api/mcp (Bearer)  ──────────▶ withMcpAuth → token.userId → tools
```

Plugin configuration in `lib/server/auth.ts`:

```ts
mcp({
  loginPage: '/login',
  oidcConfig: {
    consentPage: '/oauth/consent',
    requirePKCE: true,
    allowDynamicClientRegistration: true,
  },
})
```

Default scopes and token lifetimes. `baseURL` and `trustedOrigins` already come
from `appUrl` / `appOrigins`, so discovery is correct on production, on a
preview's branch alias and on its unique host.

**Forcing consent.** A `hooks.before` in `auth.ts`, `forceConsentOnAuthorize`,
matches the `/mcp/authorize` path and *sets* `ctx.query.prompt` to `'consent'`
(`{ ...ctx.query, prompt: 'consent' }`) before the plugin reads it — the
plugin compares `prompt` exactly, so appending to it would not do. Because the
plugin saves `ctx.query` into its `oidc_login_prompt` cookie when it sends a
signed-out user to `/login`, the resumed request after sign-in carries the
forced prompt too. Two more `hooks.before` close gaps the plugin itself leaves
open around that same flow: `refuseUnconsentedToken`, on `/mcp/token`, refuses
a code whose pending verification value still has `requireConsent: true` (the
library never checks that flag at the token endpoint, only `/oauth2/consent`
does, and the pending code travels in the consent page's own url); and
`refuseForeignConsent`, on `/oauth2/consent`, refuses a code whose `userId`
isn't the session user's (the library's own check there is only that *a*
session exists). All three read `ctx.context.internalAdapter` directly —
internal Better Auth API, worth rechecking on an upgrade.

**Login handoff.** The plugin's own resume — answering the sign-in request
itself with a redirect onward to authorize — arrives as a 302 that `fetch`
follows silently, so the browser never leaves the login form and the
authorization is lost (confirmed in a real run). A `hooks.after` on
`/mcp/authorize`, in the same `hooks` block, expires the plugin's
`oidc_login_prompt` cookie to switch that resume off entirely. In its place,
the login and signup pages read the pending authorize request off the query
(`oauthAuthorizeQuery` / `OAUTH_AUTHORIZE_PATH` in `lib/schemas/auth.ts`),
carry it across the link between the two pages, and after a successful sign-in
or sign-up do a full `window.location.assign` to
`/api/auth/mcp/authorize?<query>` — signed in by then, so the request
continues on to consent. A new sign-in path needs the same handling.

### Consent page — `app/(auth)/oauth/consent/`

Centered-card layout, like `/login`. Requires a session; without one it
redirects to `/login`. Reads `consent_code`, `client_id` and `scope` from the
query and looks up the client's registered name. Copy:

> **"<name>" wants to connect to your Creator Commerce account**
> It will be able to read your products, sales, purchases, downloads and
> account basics. It cannot change anything.
> The name is chosen by the app itself — only allow apps you set up.

Allow and Deny post to `/api/auth/oauth2/consent` through the Better Auth
client and follow the redirect it returns. The client lookup is a DAL read
(`lib/server/dal/oauth-clients.ts`, `getOAuthClientName(clientId)`) — pages do
not query tables.

### Guide — `connect-your-ai`

A new `HELP_TOPICS` entry, so Cece can answer "can I use this from Claude?":
the server url (`<app url>/api/mcp`), that the client will open a browser to
sign in and approve, that access is read-only, and that it is the same set of
lookups Cece uses. The topic list in `get_help_topic`'s description picks it up
automatically.

## Verification

Gabi runs each:

1. `npx @modelcontextprotocol/inspector` against
   `http://localhost:3000/api/mcp`: the OAuth flow signed out and signed in;
   the consent screen with Allow and with Deny; each of the nine tools; links
   absolute; no email address in any output.
2. A real client: `claude mcp add --transport http creator-commerce
   http://localhost:3000/api/mcp`, then "how are my sales this month?".
3. Negative: no token → 401; a forged or expired token → 401; user B's token
   never returns user A's data.
4. A preview deploy: discovery and the full flow on the branch alias host.
5. Cece: "can I use this from Claude?" answers from `connect-your-ai`.

## How the open questions were settled

- **The installed plugin's behaviour with a mutated `ctx.query.prompt` in a
  before-hook, on both the signed-in and the resumed-after-login path.**
  Settled in Task 1 (`fc37f78`): traced `runBeforeHooks` /
  `dispatchAuthEndpoint` in `better-auth/dist/api/dispatch.mjs` and confirmed
  the hook's returned `{ context: { query: {...} } }` is folded over the
  endpoint's own context with the hook's keys winning (`defu(obj, defaults)`
  gives `obj` priority), so `prompt: 'consent'` reaches the handler regardless
  of what the client sent. Task 3 (`fb3e26e`) separately confirmed the
  resumed-after-login path: the `hooks.after` on `/mcp/authorize` still runs
  even when the handler threw a redirect (the thrown `APIError` is caught and
  turned into a plain result object before `runAfterHooks`, not a `Response`
  that would short-circuit it), and its `Set-Cookie` physically removes the
  plugin's original cookie entry rather than merely following it — so the
  forced prompt and the cookie expiry both take, on both paths.
- **The shape of the sign-in response when the plugin's after-hook redirects,
  and how the Better Auth client surfaces it.** Made moot in Task 3: rather
  than parse that response, the `hooks.after` above turns the plugin's
  in-response resume off entirely (by expiring `oidc_login_prompt` before it
  can be read back), so the login and signup forms never need to detect or
  follow it. They carry the pending authorize request themselves
  (`oauthAuthorizeQuery`) and, on a successful `signIn.email`/`signUp.email`,
  do their own `window.location.assign` back to `/api/auth/mcp/authorize`.
- **`mcp-handler`'s API for the installed version (stateless options, how it
  receives an auth-derived context), and its compatibility with Next 16.**
  Settled in Task 2 (`3d5762b`): `createMcpHandler`'s options
  (`McpHandlerOptions`, `node_modules/mcp-handler/dist/index.d.mts`) have no
  `basePath` and default to stateless Streamable HTTP (`legacy: 'stateless'`
  in `@modelcontextprotocol/server`) with no auth-context parameter — identity
  comes from the closure over `{ userId: token.userId }` in the
  `initializeServer` callback, not from anything the handler passes in. The
  route follows the same `export const POST = handler` convention already
  used by `app/api/cece/route.ts`, confirmed against
  `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md`
  as nothing version-specific to adjust for.
